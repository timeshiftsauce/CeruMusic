## 两次真实覆盖升级

任务书要求阶段一和阶段四各一次。建立两个相互独立的 Windows 虚拟机快照：都先安装官方已发布的 2.4.0，再在旧软件中装入历史音源、静态 header 插件和支持子插件的适配器。通过旧软件实际授权、改变配置、导入子插件，设置不同启用状态和顺序。记录原列表及 `plugins/` 文件的 SHA-256 后完全退出软件。

1. 第一个快照覆盖安装上列阶段一原候选，核对旧插件、排序、启用状态、权限、配置、存储和子插件。旧音源须能搜索、解析和显示歌词。关闭并重启后再次核对。
2. 第二个快照覆盖安装最终 2.5.0 候选，重复全部保留检查，再安装 v3 页面和音源插件，确认两代并存、四处页面挂载、严格模式和停用恢复。此次只证明最终版本包含阶段四能力，不回填为历史上已经执行过的阶段四验收。
3. 每次均核对已有插件文件未被改写；除新插件追加条目外，旧状态不能改变。在快照副本中损坏一个测试插件，确认它保留在列表中并说明原因；使用相同 ID 的有效插件修复，其他插件保持原状。

不可通过先卸载旧版、清空资料目录或手工迁移数据来代替覆盖安装。两次结果单独记录，不把同一次结果填写两遍。

可在每次升级前后用 Node.js 运行附带工具，减少漏核对文件的可能。退出测试软件后，在交付目录执行；路径替换为该虚拟机实际测试资料目录，基线文件放在 `plugins` 外：

```powershell

# 在虚拟机中执行对应覆盖升级并完成界面检查，再完全退出测试软件

```

第二个独立快照使用另一份基线（如 `final-before.json`）。工具只读取插件文件，保存内容哈希和 `state.json`；不会运行插件或改写资料，不覆盖已有基线，遇到符号链接/目录联接会拒绝继续。旧文件改变、丢失或已有状态改变时退出码为 1；新文件和新增状态会单列而不误报为旧数据丢失。它不验证 UI、解密后的凭据、音频或子插件实际运行，不能替代人工验收。若测试步骤主动改了配置，先记录该操作，不能忽略差异后仍宣称原值未变。

## 物理 DLNA 与第二台 LAN 设备

使用专用测试网络、实际 DLNA 接收器与第二台设备。用开发包创建 `encrypted-source` 的 JS/TS 示例，在测试版开发者模式中加载，分别选择内置 AES-CTR、WASM 变换和本机明文服务三个提供者。

1. 在本机分别播放三个提供者；随后投放到真实接收器，确认发声、进度前进、停止/续播正常。使用长于样例三秒的已授权测试音频验证非零位置跳播；三秒样例内的缓冲跳播不能证明远程 Range 处理。
2. 默认仅有 `network.serve` 时，在第二台设备访问测试主机局域网 IP 与实际分配端口，必须无法访问。确认测试网络连通后，再为专用服务声明并授予 `network.serve.lan`、以 `lan: true` 启动，第二台设备应能访问。
3. 撤销 LAN 权限、停用和卸载分别检查：监听关闭、在途连接结束，之后不能继续访问。端口读取实际运行结果，不假定固定端口。
4. 下载加密测试音频，用系统播放器打开保存文件；核对内容已解密且可播放。记录接收器型号、固件、网络和失败阶段，不将本机 HTTP 通过写成物理投放通过。

1. 完成实际扫码或网页登录，核对昵称、头像及账号归属。取消一次登录，确认没有新增连接；再添加第二个账号，分别切换、退出并重启软件核对持久化。
2. 进入“我喜欢”和歌单，核对当前账号的数据。只在明确开启同步后测试一首歌的收藏及取消收藏，核对平台端结果；关闭同步后本地操作不应写入平台。
3. 撤销或使凭据过期，确认提示重新登录、受保护操作不会借用其他账号。续期后连接身份保持，切换音源期间的迟到登录结果不会夺回用户的新选择。
4. 凭据明文不出现在截图、日志或报告中；记录方式、平台、插件/候选版本及结果即可。
